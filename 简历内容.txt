【项目简介】

基于 MCP 协议的 14 工具 AI Agent 旅行规划应用。LangGraph ReAct Agent 协同 5 个 MCP Tool Server，完成路线规划、POI 搜索、联网检索、知识库 RAG、流式交互、技能自进化等全链路。自建 12 用例评估框架，复现 8 项 Agent 工程化问题并逐一解决。


【设计思考】

1. 不信任 LLM 的输出——为什么把地图链接从 LLM 剥离

LLM 看到店名后倾向于自行编造百度地图链接，但坐标是训练数据里没有的，错得离谱。本质问题是：LLM 善于语言生成，不擅长确定性数据计算。

思路：设计上把"说什么人话"（LLM 负责）和"链接指哪里"（传统代码负责）彻底分开。搜索结果坐标存入后端缓存，前端等 AI 说完话后异步注入导航按钮。LLM 全程不碰坐标。

启发：Agent 系统的不可靠性往往来自让 LLM 做了不该它做的事。识别 LLM 的能力边界、把确定性计算剥离出来，是降低 Agent 错误率的核心方法。


2. 不给所有环境打补丁——为什么回退到纯 Python 方案

Windows Conda 环境下，onnxruntime DLL 加载失败、ChromaDB 段错误、sentence-transformers 版本冲突。修一个冒出两个，改依赖版本会引起连锁反应。

思路：放弃"修环境"的思维，改为"换方案"。jieba 分词 + sklearn TfidfVectorizer + 余弦相似度，三个都是纯 Python，零二进制依赖。效果不如专用 embedding 模型，但可用性和可维护性完胜。

启发：个人项目的技术选型，可维护性优先级高于精度。一个永远能跑的 70 分方案，胜过需要特定环境才能跑的 90 分方案。


3. 不让上下文无限膨胀——为什么压缩而不是扩大窗口

旅游规划一次调 15+ 工具，返回结果全堆在对话历史里。通用做法是扩大上下文窗口，但不治本——窗口再大也会满，且 token 成本线性增长。

思路：(1) 句子级 TF-IDF 评分——保留数字和地名的句子，丢弃"向前步行 10 米"类细节；(2) Plan Mode——搜索阶段和规划阶段分离，搜索结果写入文件，主 Agent 的上下文只保留结论摘要。

启发：与其靠扩大资源解决问题，不如从源头减少浪费。上下文管理不是硬件问题，是架构问题。


4. 不只依赖 LLM 推理——为什么引入代码执行

Agent 面对"帮我把这 10 家密室逃脱按性价比排序"时，纯 LLM 推理需要逐一比对评分和价格，慢且容易漏。多次工具调用来回拼接数据也不优雅。

思路：借鉴 GenericAgent 的核心设计——用单一可编程工具替代 N 个专用工具。沙箱里跑 Python，Agent 自己写代码处理数据。不替代已有的专用工具（查天气、查路线），而是作为兜底——当专用工具覆盖不到时，让 Agent 自己造工具。

启发：Agent 的工具设计应该分层。专用工具覆盖高频场景，通用可编程工具覆盖长尾。两者互补，不是替代关系。


5. 不用通用大模型——为什么选 DeepSeek

最直接的原因是 ChatTongyi 没有 API Key，项目启动时跑不起来。切换到 DeepSeek 后发现它的中文能力并不弱于更贵的模型，且 API 兼容 OpenAI 格式，LangChain 集成零成本。

启发：LLM 选型的第一原则是"能跑起来"，第二原则才是"哪个更强"。个人项目不必追最新模型，稳定可用优先。


6. 不只存"去过哪"——为什么按评分分级

常规做法是记录去过的地方然后排除。但"去过"不等于"不想再去"——评分 4.5 的店用户可能想二刷，评分 1 的才该排除。

思路：6 维度评分（性价比、拥挤度、出片指数、趣味性、符合预期、推荐度）。根据综合评分分三档处理：高分优先推荐，中等作为备选，低分严格排除。未评分的默认保守处理。

启发：用户数据的使用需要区分粒度。同样是"去过"，背后的态度完全不同。
