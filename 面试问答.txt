面试问答——针对简历每一行的预期问题与回答思路


【项目简介部分】

Q：14 个工具都是什么？为什么这么多？
A：分五类——天气 3 个（当前/预报/贴士）、路线 4 个（公交/驾车/步行/附近搜索）、搜索 3 个（网页搜索/深度阅读/POI 搜索）、知识 2 个（本地知识库/技能库检索）、通用 2 个（计算器/code_run）。不是一次设计的，是逐步加的——每次发现 Agent 缺某种能力就加一个。关键设计是 MCP 协议让加工具只需要写一个新文件加一行配置，不用改 Agent 主逻辑。

Q：5 个 MCP Tool Server 之间怎么通信？为什么用 stdio 而不是 HTTP？
A：MCP 的 stdio 传输——每个 Server 是独立子进程，Agent 通过标准输入输出和它们通信。选 stdio 是因为：(1) 不需要端口管理；(2) 进程崩溃隔离，一个 Server 挂了不影响其他的；(3) 个人项目不需要跨机器部署。

Q：LangGraph ReAct Agent 和直接用 LangChain 的 Agent 有什么区别？
A：LangGraph 是更底层的状态图框架，把 Agent 的决策过程建模成有向图。ReAct 模式是 Reasoning + Acting 循环——LLM 先想该调哪个工具，调完观察结果，再想下一步。LangGraph 的好处是自带 checkpoint、自带 streaming、可以精确控制执行路径。LangChain 的 create_agent 是对它的封装，但版本兼容有问题所以我直接用底层 API。


【设计思考 1——不信任 LLM 的输出】

Q：你说"LLM 编造百度地图链接"，怎么发现这个问题的？
A：测试时点推荐的链接跳过去发现定位不对。追回去看 AI 的输出，发现链接里的坐标和高德 API 返回的真实坐标不一样。LLM 看到店名"关你鬼室密室逃脱"后，凭训练数据里的记忆拼了一个 URL，但里面的经纬度是错的。

Q：既然是错的，为什么 LLM 还会这么做？
A：LLM 不理解"坐标必须精确"。它学到的是"推荐地点时附上地图链接是好的用户体验"，所以会自动生成。但它没有访问高德 API 的能力，只能根据训练数据里的类似 URL 格式去猜。这是 LLM 的本质缺陷——它分不清什么是它能做的（语言生成），什么是它不该做的（确定性数据）。

Q：你的解决方案是"把生成权从 LLM 剥离"，具体怎么做的？
A：搜索结果回来时，坐标已经存在后端 JSON 文件里了。前端通过 SSE 拿到文件 ID，fetch 到数据，等 AI 说完话后在 DOM 里注入 `<span onclick="openAmap(...)">` 按钮。AI 全程不碰坐标，只负责"推荐理由"这种人话部分。

Q：这个思路能推广吗？
A：能。Agent 系统里有一个通用原则——识别 LLM 的能力边界，把确定性计算剥离给传统代码。这个原则后来用在了知识库检索和技能库匹配上——都是 TF-IDF 计算相似度，不是让 LLM 猜。


【设计思考 2——回退到纯 Python 方案】

Q：ChromaDB 为什么会段错误？
A：Windows Conda 环境下的 DLL 加载问题。ChromaDB 依赖 onnxruntime 做 embedding，但 onnxruntime 的 C++ DLL 在这个环境里加载失败。不是代码 bug，是环境兼容性问题。

Q：为什么不用 Docker 解决环境问题？
A：写了 Dockerfile，但 Docker 在 Windows 上需要 WSL2，个人开发环境不想多一层虚拟化。而且这个决策背后有一个原则——个人项目可维护性优先于技术先进性。一个双击就能跑的纯 Python 方案，比需要配环境才能跑的方案更有生命力。

Q：TF-IDF 做语义检索，和 embedding 模型比差在哪？
A：TF-IDF 是关键词匹配，理解不了同义词。比如搜"火锅"找不到"涮羊肉"。但对于旅游攻略场景，用户搜索词和文档关键词重叠度通常很高（"成都火锅""广州密室逃脱"），所以实际差距不大。如果后续数据量大到关键词匹配不够用，再考虑升级。

Q：面试官可能追问——"你怎么评估 TF-IDF 够用？"
A：跑过几个 case：搜"广州塔有多高"→ 命中"广州塔攻略"（TF-IDF 0.365）；搜"北京故宫"→ 无结果（正确，库里没有）。核心指标不是检索质量多高，而是"不会返回无关内容误导 Agent"。


【设计思考 3——上下文压缩】

Q：你说"扩大上下文窗口不治本"，为什么？
A：因为 Agent 的上下文消费是线性的——每次工具调用都新增历史，10 次调用就 10 条新消息。窗口从 32K 扩到 128K，只能延缓问题，不能解决问题。而且窗口越大推理越慢、越贵。更好的思路是从源头减少上下文浪费。

Q：你用 TF-IDF 做句子评分，会不会把重要信息误删？
A：有风险，所以有两层兜底：(1) 只压缩 8 轮以前的旧消息，最近的消息保留原文；(2) 如果 TF-IDF 计算失败（比如句子太少），回退为头尾保留——保留开头 100 字加结尾 50 字。实测压缩后规划质量没有退化。

Q：Plan Mode 和普通模式的区别？
A：普通模式是"搜到啥用啥，全堆上下文"。Plan Mode 把"搜索"和"规划"分成两阶段——搜索阶段把攻略写进文件，规划阶段只读文件里的结论摘要。主 Agent 的上下文里不再有"6000 字攻略全文"，只有"这篇攻略推荐了 8 个景点，其中 3 个在同一个地铁线上"。

Q：这么做的代价是什么？
A：多了一次文件读写，增加 ~0.5s 延迟。但换来的是后面每次 LLM 推理都不需要重传搜索阶段的冗长输出。对于多轮对话场景，总 Token 消耗下降。


【设计思考 4——引入代码执行】

Q：code_run 和 calculate 工具有什么区别？
A：calculate 是预定义的数学表达式解析器，只能一次算一个式子。code_run 是完整 Python 沙箱，可以写循环、排序、条件判断。二者是互补的——简单计算用 calculate，复杂数据处理用 code_run。

Q：安全问题怎么解决的？
A：(1) 子进程执行，不共享主进程内存；(2) 30 秒超时，避免死循环；(3) 禁止 __import__, open, os, sys, eval, exec 等危险操作；(4) 独立工作目录 sandbox/。本质上不相信 AI 写的代码是安全的，所有限制都在系统层面实现。

Q：面试官追问"什么时候该用 code_run，什么时候不该用？有什么判断标准？"
A：Prompt 里写了三条规则——(1) 现有工具无法一步完成；(2) 涉及 3 条以上数据的操作；(3) 不是实时信息查询。如果都满足才用。用规则而非让 LLM 自行判断，是因为 LLM 倾向于过度使用新工具。

Q：这是借鉴的 GenericAgent，你怎么评价这个设计？
A：GenericAgent 的核心思想是"少即是多"——给 Agent 一个可编程的工具，让它自己组合能力。我们取了这个思路但没照搬——GenericAgent 只有 9 个工具且 code_run 占核心地位，我们是 code_run 作为兜底，专用工具覆盖高频场景。分层设计比全通用或全专用都更实际。


【设计思考 5——DeepSeek 选型】

Q：为什么不用 GPT-4 或 Claude？
A：(1) 项目启动时 ChatTongyi 没 API Key，跑不起来；(2) DeepSeek API Key 已经配好了；(3) 中文能力够用；(4) 价格远低于 GPT-4/Claude。个人项目的 LLM 选型，能跑起来比模型多强更重要。

Q：有人说 DeepSeek 的 function calling 不够稳定，你怎么看？
A：确实遇到过工具调用格式偶尔不符合预期的情况，但 MCP 协议在工具返回后会做格式校验，拦截了大部分非法调用。而且 LangGraph 的 checkpoint 机制保证了即使某次调用失败，也不影响整个会话。


【设计思考 6——评分分级】

Q：6 维度评分怎么设计的？
A：性价比、拥挤度、出片指数、趣味性、符合预期、推荐度。选这 6 个是因为它们覆盖了旅游决策的主要维度——不是简单地"好/不好"，而是"好在哪/差在哪"。

Q：评分后怎么影响下次推荐？
A：评分 ≥4 可以再推荐（用户喜欢），2-3 作为备选（一般般），<2 严格排除（不喜欢），没评分默认排除（保守）。关键设计是——"去过没评分"和"去过不喜欢"处理方式不同，前者只是不主动推，后者明确禁止。

Q：这个评分系统为什么放在前端弹窗而不是让 Agent 做？
A：评分是结构化数据收集，用传统表单比让 LLM 解析自然语言更可靠。而且评分弹窗和"我去过了"按钮绑定——用户必须先确认真的去了，才能进入评分流程。避免"没去也评"的数据污染。


【评估体系】

Q：12 个用例够吗？
A：对于个人项目来说够了。12 个覆盖了核心场景——天气/路线/POI/知识库/旅游规划。关键不是数量，是有没有持续在跑。每次改代码后跑一次评估，能看到哪些用例从通过变失败。

Q：通过率 83.3%，为什么不到 100%？
A：剩余 16.7% 的失败是因为 Plan Mode 重排了工具调用顺序——Agent 遵循"先搜本地→再联网"策略，和部分用例期望的"直接调用某工具"不一致。这是设计行为，调整测试用例即可覆盖。

Q：为什么自己写评估框架而不是用 LangSmith 等现成的？
A：LangSmith 确实更强大，但它是一个外部服务，有注册门槛和成本。自建框架的好处是——零依赖、可定制、完全可控。而且自己写能更深入理解 Agent 的评估指标体系。对于学习阶段和个人项目，自建比直接接入更值。


【项目整体】

Q：这个项目最让你骄傲的技术点是什么？
A：不是 code_run，也不是评估框架。是在做的过程中形成的一条方法论——"识别 LLM 的能力边界，把不该它做的事剥离出去"。这个思路串起了导航链接治理、知识库检索、技能匹配、上下文压缩四个模块的设计决策。从最初的"让 LLM 干啥就干啥"到后来的"LLM 负责语言，传统代码负责计算"，是理解 Agent 工程化最核心的一次认知升级。

Q：如果让你重做，你会改什么？
A：(1) 先建评估框架再写代码，而不是反过来；(2) 工具返回的数据从一开始就结构化存储，不给 LLM 编造的机会；(3) 上下文管理从第一天就做，而不是等消息数膨胀到 40 条才被动应对。

Q：你觉得这个项目在 Agent 方向上还有什么可以做的？
A：多 Agent 协作——把探索、规划、校验拆给三个 Agent 分别做。现在是一个 Agent 包办所有事，虽然 Plan Mode 做了一些分离，但不是真正的多 Agent 架构。这是更大的话题，需要 LangGraph 的 subgraph 能力。
